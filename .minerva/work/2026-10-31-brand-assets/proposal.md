# Proposal: brand-assets

**Date**: 2026-10-31
**Status**: Draft

## Goal
Every place the app shows an icon or logo shows the Fencepost "Picket F" mark instead of the Expo and React Native defaults: the iOS app icon (an Icon Composer bundle on the chalkboard), the Android adaptive icon (chalkboard background), the splash screen (board color and ink following the system scheme), the web favicon, and the in-app title in the topics sheet. The theme palette the mark is drawn from is documented in README and kept in sync with `app.json` and the README by a test, and every raster asset can be regenerated from one geometry module and that palette with one command.

## Why
The request, verbatim, after three logo candidates were shown on an artifact page (A posts-and-rails, B picket F, C marker sketch), each as an icon on blue, whiteboard and chalkboard tiles:

> "B chalkboard variation, can we make sure to update the theme and document the theme colors and such if we have not already, go ahead and also replace and update logos / splash / etc"

Facts verified at intake:
- `assets/images/{icon,splash-icon,favicon,android-icon-foreground,android-icon-background,android-icon-monochrome}.png` and `assets/expo.icon/` (Icon Composer bundle: `expo-symbol 2.svg` + `grid.png`, automatic-gradient fill) are the `create-expo-app` defaults. `app.json` splash is `#208AEF` and the adaptive-icon background is `#E6F4FE`; neither is a theme color.
- The palette lives in `src/theme/colors.ts` (`lightColors`/`darkColors`: board, dot, card, ink, muted, rule, wash, blue, blueWash, red, redWash, green, greenWash, gold, goldInk, goldWash) and feeds `tamagui.config.ts`. It is framework-free by design. Fonts: Bricolage Grotesque (display), Atkinson Hyperlegible (body), JetBrains Mono (code), Kalam (marker). The colors file's header cites "the design spec", which is not in the repo. README has no theme or brand section; `.minerva/reference/` is empty.
- In-app there is no Expo artwork; the app name is text in the topics sheet title and the welcome card eyebrow.
- Mark B geometry (1024 viewBox): top rail `rect x=300 y=356 w=440 h=96 rx=48` (ink), lower rail `rect x=300 y=548 w=360 h=96 rx=48` (accent), picket `M300 312 L364 228 L428 312 V752 a44 44 0 0 1 -44 44 H344 a44 44 0 0 1 -44 -44 Z` (ink). Chalkboard: background `darkColors.board` #16211d, ink `darkColors.ink` #eaf0ec, accent `darkColors.blue` #8ab6ff.

Prebuild flattens the iOS PNG icon (`removeTransparency`) when the PNG path is used.

Vitest includes `src/**/*.test.ts` and `scripts/**/*.test.ts`; coverage thresholds measure `game`, `cards`, `server`, `store`, `lib` only. `/ios` and `/android` are gitignored. Prettier ignores `*.md`.

## Approach
One work unit, one PR, unphased.

1. **One geometry source.** `src/theme/brand-mark.ts` exports the mark's three shapes as plain constants (no React, no react-native-svg) plus the 1024 viewBox. It is the master. Everything else is derived from it and the palette.
2. **Renderer** `scripts/brand/render-assets.ts`, run by the bare `package.json` script `"brand:render": "tsx scripts/brand/render-assets.ts"` (bare so knip infers it as an entry; `knip.json` is guarded and is not edited). It imports `lightColors`/`darkColors` and the geometry, builds SVG strings from shared helpers (no near-duplicate literals, for jscpd), and screenshots them with Chromium from `@playwright/test` at a fixed viewport, `deviceScaleFactor: 1`, explicit `clip`, no text and no fonts. It writes:
   - `assets/brand/mark-light.svg`, `mark-dark.svg`, `icon.svg`: the generated vector forms, committed for designers and for the README; outputs, not masters.
   - `assets/images/icon.png` 1024x1024: chalkboard tile, chalk F, blue rail, drawn over an opaque rect. Used by top-level `icon` (Android legacy icon; iOS only if the bundle is dropped, in which case prebuild flattens it).
   - `assets/images/android-icon-foreground.png` 512x512 transparent, the mark inside the 66% safe zone; `android-icon-monochrome.png` 512x512 white mark. `android-icon-background.png` is deleted; the adaptive background is `backgroundColor`.
   - `assets/images/splash-icon.png` (whiteboard ink + blue) and `splash-icon-dark.png` (chalk ink + light blue), 512x512 transparent.
   - `assets/images/favicon.png` 96x96 chalkboard tile with rounded corners.
   - `assets/fencepost.icon/icon.json` + `Assets/picket-f.svg` + `Assets/accent-rail.svg`, exactly the bundle actool compiled at intake, with the fill computed from `darkColors.board`.
   Determinism is a local property: a second run on the same machine and Playwright version leaves `git status` clean. Chromium output can differ across OS and versions, nothing in CI regenerates assets, and the committed PNGs are the source of record. README says regeneration is a manual local step and to review the image diff.
3. **`app.json`**: `icon` stays `./assets/images/icon.png` (new content); `ios.icon` -> `./assets/fencepost.icon`; `android.adaptiveIcon` -> `foregroundImage`, `monochromeImage`, `backgroundColor: "#16211d"`, `backgroundImage` removed; `web.favicon` unchanged path; `expo-splash-screen` -> `backgroundColor: "#eef1ef"`, `image: ./assets/images/splash-icon.png`, `imageWidth: 120` (the mark is a single glyph; 76 was sized for the Expo wordmark), `dark: { backgroundColor: "#16211d", image: ./assets/images/splash-icon-dark.png }`. `assets/expo.icon/` is deleted.
   **Decision: the splash follows the system scheme, not "always chalkboard".** `userInterfaceStyle` is `automatic` and the app paints a whiteboard in light mode, so a chalkboard splash would flash into a white board. The icon and the Android adaptive background are the chalkboard, which is what "B chalkboard variation" named on the artifact page (the splash was shown on blue there, not as a variant). The iOS dark and tinted icon appearances are left to the system over the solid dark fill; no `fill-specializations` are written. This divergence from a literal reading of the seed is named in the final report.
4. **Palette sync test** `src/theme/colors.test.ts` (inside the Vitest include): every `#rrggbb` in `app.json` is a value exported from `colors.ts`, and the README palette table (the markdown table rows under the "Theme and brand" heading whose first cell is a token name) lists exactly the palette's token names with their light and dark values. Hex values elsewhere in the README (for example the white monochrome layer) are not checked. This is what keeps the three from drifting.
5. **In-app**: `src/components/ui/brand-mark.tsx` draws the mark with react-native-svg from `useTheme()` tokens (ink + blue), importing geometry from `src/theme/brand-mark.ts`, with `testID="brand-mark"` and `aria-hidden` (decorative). The topics sheet title becomes mark + the unchanged "Fencepost" text, so the accessible name stays "Fencepost". No existing unit or e2e test queries that title (grepped). The welcome-card eyebrow stays text. The e2e starter spec asserts the mark and the "Fencepost" title are both visible when the topics sheet is open.
6. **Docs**: README gains a "Theme and brand" section after "Layout": the palette table (token, light, dark, use), the four type faces and roles, the dot grid, the mark and the fencepost-error pun, the asset inventory with sizes and which `app.json` key uses each, and `npm run brand:render` with the local-determinism note. `src/theme/colors.ts`'s header points at that section. NOTES.md "Day to day" gets one line: a native asset change such as this icon takes the build path.
7. **Verification** (local; CI cannot): `npx expo prebuild --platform ios --no-install` and `--platform android --no-install` in the worktree (gitignored output); `xcrun actool` on the generated iOS asset catalog plus the `.icon` bundle with `--app-icon fencepost --include-all-app-icons`, requiring zero errors and zero warnings; the emitted `60x60@2x` PNG is opened and looked at; `sips -g hasAlpha` on `icon.png` is recorded; `npm run guard` and `npm run e2e` pass. **Fallback**: if the real prebuild catalog fails to compile with the bundle, `ios.icon` is removed and iOS uses the flattened PNG `icon`, which Expo documents, and the proposal records that. **Residual risk, accepted**: local actool is Xcode 26.2 and EAS builds with Xcode 27.1, so a bundle that passes here could still fail or render differently there, and that shows only as a red run on expo.dev after merge. Recovery is the same fallback as a follow-up PR (remove `ios.icon`; the PNG `icon` takes over and the change takes the build path again). NOTES.md "When something goes wrong" gets that line. If knip reports the renderer as unused despite the bare script, the run stops and reports that `knip.json` needs the owner's label; it is not edited here.

### Candidates considered
Criteria: (1) assets derive from the documented palette; (2) anyone can regenerate them; (3) no guarded path is touched; (4) smallest tooling surface; (5) the native config is verified before merge, since CI can't.

- **A (recommended). One geometry module + a Chromium renderer from `@playwright/test`, outputs committed.** Meets 1, 2, 3, 5. Costs one script of roughly 150 lines plus small helpers and one npm script (criterion 4). Determinism is local only (above).
- **A'. Same, rendering with `@resvg/resvg-js` or `sharp`.** Deterministic across platforms and no browser launch, but a new native devDependency (lockfile, osv-scanner, `expo install --check`), against criterion 4. Rejected for this unit; noted in README as the upgrade if cross-machine drift ever matters.
- **B. Hand-export the PNGs once, commit them, no script.** Meets 3, 4, 5. Fails 1 and 2: the palette and the rasters drift silently and the next change is done by hand.
- **C. A config plugin rendering at prebuild time.** Meets 1 and 2 but adds a dangerous mod to every prebuild and the committed repo never shows the icon; worst on 4 and 5.

Why A over B: the user asked for the theme to be the documented source of the brand, which B can't honour; A uses only existing devDependencies.

### Out of scope
Android package id and Play assets, App Store screenshots, the display name, any `.github/`, `AGENTS.md`, `knip.json` or tsconfig edit, an EAS build before merge, the welcome-card eyebrow, web manifest or apple-touch-icon (`web.output: server` uses only the favicon).

## Success criteria
1. `assets/expo.icon/` and `assets/images/android-icon-background.png` are deleted; `git grep -il "expo-symbol\|grid.png" -- assets app.json` returns nothing; every file under `assets/` is written by the renderer.
2. `npm run brand:render` runs from a clean checkout and writes every raster, the SVG outputs and the `.icon` bundle; a second run on the same machine leaves `git status --porcelain` empty. README states this is a local, manual step and that Chromium output can differ across machines.
3. `app.json` references `./assets/fencepost.icon`, both splash images with a `dark` block, the adaptive icon foreground + monochrome + `backgroundColor` and no `backgroundImage`, and the favicon; `src/theme/colors.test.ts` passes, asserting every hex in `app.json` is a palette value and that the README palette table rows match the palette's tokens and values exactly.
4. Throwaway iOS and Android prebuilds succeed; `xcrun actool` compiles the real generated iOS catalog with the `.icon` bundle with zero errors and zero warnings; the emitted `60x60@2x` PNG was viewed and shows the mark; `sips -g hasAlpha assets/images/icon.png` is recorded in the scratchpad; the Android `res/mipmap-*` hold generated launcher PNGs. Nothing generated is committed. If the fallback fired, `ios.icon` is absent and the proposal says why.
5. `src/components/ui/brand-mark.tsx` exists, imports geometry only from `src/theme/brand-mark.ts` (the renderer imports the same module; jscpd reports 0%), and the e2e starter spec asserts `brand-mark` and the "Fencepost" title are visible in the open topics sheet; `npm run e2e` passes.
6. README has the "Theme and brand" section described in Approach 6, `src/theme/colors.ts` points at it, NOTES.md "Day to day" names the asset-change build path, and NOTES.md "When something goes wrong" names the remove-`ios.icon` recovery.
7. `npm run guard` exits 0 and `git diff --name-only main...HEAD` contains no path listed in `.github/guardrail-paths.txt`.

None. Two things are decided rather than asked: the splash follows the scheme (Approach 3), and this merge produces a TestFlight build, which is the point.
