# Proposal: fencepost-v1

**Date**: 2026-10-29
**Status**: Shipped (2026-10-29)

## Goal
Build Fencepost v1 as specified in the build handoff (`~/Downloads/FENCEPOST_HANDOFF.md`, copied into the unit as `.minerva/work/2026-10-29-fencepost-v1/handoff.md`): an Expo app (iOS, Android, web from one codebase) that plays a swipe-up feed of tap-to-answer logic-puzzle cards of five types (flaw, break, trace, model, order), with a bundled 6-card starter deck, the full game rules of handoff §7 (scoring, combos, 2x and boss cards, daily streak, ranks, rematches, skip, "card was wrong", celebrations, haptics, verdict words), the §9 visual design (whiteboard/chalkboard themes, marker circle, transitions, verdict panel, top bar, topics/stats sheet), on-device persistence, and a small stateless server (Expo Router API routes served by `expo-server`'s Express adapter) that generates cards on demand through OpenRouter via the Vercel AI SDK and streams them to the app as NDJSON — plus the Docker/Fly.io deployment artifacts.

## Why
The handoff defines a complete v1 that replaces the current repo contents (the untouched `create-expo-app` SDK 58 tabs template). The audience is senior engineers who want quick, realistic logic puzzles; the endless LLM feed is the product, and the starter deck + offline engine make it playable without the server.

## Approach
Built in the handoff's milestone order (§14, milestones 1–9) inside one work unit shipped as one PR. Each milestone's checks ran before the next one started, and each milestone commit left `tsc` and the tests green. Two replans changed the plan (replan.md): iOS is verified in Expo Go because SDK 58 dev builds need Xcode 26.4+, and criterion 12's "single machine" is enforced by the documented deploy flags rather than by `fly.toml`. Two independent code reviews ran, and their findings were fixed in this unit. Where the handoff and the project's `AGENTS.md` disagree, `AGENTS.md` wins; where the handoff and current official docs disagree on an API, follow the docs and note it in `NOTES.md`. Every package is installed with `npx expo install` (it falls back to npm for non-Expo packages); every Expo/AI SDK/Tamagui API is checked against current docs (Expo SDK 58 versioned docs) before use.

Stack (handoff §3):
- **App:** Expo SDK 58 + Expo Router + TypeScript. Routes live in `src/app/` (AGENTS.md rule, overriding the handoff's root `app/`): `src/app/_layout.tsx`, `src/app/index.tsx` (the feed), `src/app/api/{health,cards,flag}+api.ts`. The template's tabs, explore screen, demo components/hooks/constants/assets and `reset-project` script are removed. The React Compiler (`experiments.reactCompiler`) stays on unless it breaks Tamagui or Reanimated, in which case it is turned off and noted in NOTES.md.
- **UI:** **Tamagui 2.7.7 pinned, with `@tamagui/config/v5`** (shorthands such as `bg`/`items`/`p`, and `$` tokens), extended by the §9 tokens as `light`/`dark` themes that follow the system theme. tamagui 3.1.7 rendered unstyled on the web export, and 2.7.7 has no `config/v6` (knowledge: `2026-10-29-decision-tamagui-pinned-to-2-7-7`). On web the app renders only after mount (`useSyncExternalStore`), because server-rendered HTML can't know the color scheme or the saved progress. Code text disables JetBrains Mono ligatures: CSS `font-variant-ligatures: none` on web, and U+2060 word joiners between symbols on iOS, whose Fabric text renderer ignores ligature `fontVariant`. `Tap` ignores presses that move more than 10px, so a swipe never answers a card. `metro.config.js` = `expo/metro-config` wrapped with `withTamagui`. Fonts (Bricolage Grotesque, Atkinson Hyperlegible, JetBrains Mono, Kalam via `@expo-google-fonts/*`) load before the splash hides.
- **Milestone 1 Tamagui gate:** milestone 1 passes only when a themed Tamagui screen (tokens, fonts, light and dark) (a) renders in the web export in a browser and (b) renders in Expo Go (SDK 58) on the iOS simulator (weakened from a development build — SDK 58 needs Xcode 26.4+ and only 26.2 is installed; see replan.md), with the React Compiler on or deliberately off per the rule above. Passed on the web export plus Expo Go with the compiler on. If it cannot pass with the compiler on **and** with it off, that is a load-bearing divergence: replan to plain React Native `StyleSheet` + a small token/theme hook (option B) inside milestone 1, before any card UI is written; the replan relaxes the Tamagui-specific success criterion.
- **Animation/gesture/drawing/haptics:** `react-native-reanimated`, `react-native-gesture-handler`, `react-native-svg` (marker circle), `expo-haptics`. Respect the OS reduce-motion setting (no slide/rise animation, marker circle drawn without stroke animation).
- **State:** `zustand` + `persist` over `expo-sqlite/kv-store` on iOS/Android and a `localStorage` adapter on web (platform file `storage.web.ts`; expo-sqlite on web needs wasm + COOP/COEP headers, and persisted state is only read on the client, never during server rendering), with the storage adapter and clock injectable so the store is testable in Node; progress saved debounced (~1 s) after each answer and on backgrounding.
- **Pure core (no React/RN/Expo/Tamagui/zustand imports):** `src/game/` (types, scoring, streak, ranks, serve order and rematch scheduling, skip/flag reducers, celebration decisions, verdict word choice, haptic-pattern choice, swipe-to-advance gating, prefetch & retry policy, a feed controller that consumes NDJSON events) and `src/cards/` (zod `RawCard`, `normalize` with an injected id factory and an optional fixed-id override used by starter cards, starter deck JSON, domains). Randomness (2x roll, boss roll, plan, shuffles) takes an injectable RNG so probabilities are testable. The device id is created with `expo-crypto` on the client. React components stay thin over these. Unit-tested with **Vitest** (types included in tsconfig; aliases resolved).
- **Server:** `src/server/` (prompt builder with the §8.3 prompt verbatim, plan maker with type weights + boss rule + domain rotation per device, in-memory token-bucket rate limiter per device and per IP, request validation with 4 KB cap and unknown-field rejection, `CardSource` interface with a live-generation implementation whose language model is injectable, JSON batch logging with hashed device id). Imported only from `+api.ts` files: route logic lives in `src/server/handlers.ts` as plain `(Request) => Promise<Response>` functions with injectable dependencies, the `+api.ts` files are thin wrappers, and tests import `src/server/` directly (no `expo-server` or `expo/fetch` at test runtime). The OpenRouter base URL is configurable via `OPENROUTER_BASE_URL` (defaults to OpenRouter's). `/api/cards` request order: parse+validate (400) → rate limit, consuming a token (429 + `Retry-After`) → model config present (503) → stream. Streaming uses AI SDK `streamText` + `Output.array` + `elementStream` with `@openrouter/ai-sdk-provider`. The element schema sends the strict RawCard JSON schema to the model but validates pass-through, because `elementStream` silently drops invalid elements; `normalize` validates every element, keeping plan slots aligned and drops counted. The model comes from `CARD_MODEL`, with one retry on `CARD_MODEL_FALLBACK` if the first fails, or produces nothing playable, before any card is sent, 90 s abort + client-disconnect abort, output-token cap, pings every 10 s until the first card, an `error` event mid-stream. `/api/flag` validates, rate limits, and logs one JSON line. Rate limiting checks every bucket (IP first) before charging any, and each limiter holds at most 50k keys (LRU). The IP comes from `Fly-Client-IP` only when `FLY_APP_NAME` is set, otherwise from the last `X-Forwarded-For` hop. `readBody` streams the body and stops once it passes the cap, even without `Content-Length`. Recent titles have their double quotes turned into single quotes before they enter the prompt. No test-only source exists in production code; tests inject a mock model. An unconfigured server still consumes rate-limit tokens (intentional: the order is fixed and keeps the endpoint cheap to probe). The plain-NDJSON-from-model fallback is not built unless the chosen model needs it.
- **Client fetching:** `src/lib/` NDJSON reader over `expo/fetch` streamed bodies, feeding the feed controller. API paths are made absolute with `apiUrl()` against `window.location`, because `expo/fetch` doesn't resolve relative URLs on native (verified in Expo Go on iOS against a stub). Batches start at least 20 s apart, matching the server's device refill, and a batch still open after 100 s fails with Try again. Every way a batch ends leaves a playable card or the error card: a skip starts the session, a cancel on the loading card shows Try again, and a batch with nothing playable fails. A finished or stale batch never touches the next one. prefetch a batch of 5 when ≤2 queued cards remain, only after the first answer in a session, one fetch at a time; no auto-retry on 429, one automatic retry after 3 more answers for other errors, otherwise a Try again button; cancel the in-flight request after >1 min in background, keeping arrived cards. Loading (topic + elapsed seconds), error, and welcome-back cards. When the server is unconfigured (503) the app shows the error card and the starter deck and rematches stay playable.
- **Tests beyond unit:** server tests that drive the `/api/cards` and `/api/flag` handlers with the AI SDK's mock language model (no network, no key); a Playwright end-to-end suite (`npm run e2e`) that runs the web export through `server.js` and stubs `/api/*` responses with `page.route` where a model would be needed; an eval script `npm run cards:eval -- --model <id> --batches N` that calls the generation function directly (requires `OPENROUTER_API_KEY`).
- **Deploy artifacts:** `server.js` (Express 5 + `expo-server/adapter/express`, static `dist/client`, no compression), two-stage `Dockerfile` on Node LTS (`npm ci` + `npx expo export --platform web` in the build stage), `fly.toml` per handoff §15 (`min_machines_running = 1` is only a floor; NOTES.md deploys with `fly deploy --ha=false` and recovers with `fly scale count 1`), `app.json` `expo-router` plugin `origin: https://fencepost.fly.dev` (a guess until `fly launch` assigns the name — a wrong value breaks native API calls; documented). `express` and `expo-server` are regular dependencies.

**Not done by this run (user-run, documented in `NOTES.md`):** `fly launch`/`fly secrets set`/`fly deploy` and the Fly health check against the live app (outward-facing, needs the user's Fly account); creating the OpenRouter key and its credit limit; choosing `CARD_MODEL` by running the eval against real models — so **the correctness of generated cards is unverified at ship time**, only the plumbing and validation are tested (no key in this environment); the Android emulator pass (no Android SDK installed); the production-native-build-against-Fly check (depends on the deploy); the manual simulator passes for airplane mode mid-batch, reduce motion, large text / Dynamic Type, and native swipe feel; native `expo/fetch` incremental reads against the deployed server on Android, in a release build, and over a real network (web streaming, the server's streaming, and the native read path in Expo Go on iOS against the dev server and a stub are verified); physical haptic feel; the iOS development-build compile and run (`npx expo run:ios` needs Xcode 26.4+; config-plugin effects and the custom binary are therefore unverified — see replan.md). Playwright's browser download needs network access, which this environment has. The handoff's "stop after each milestone" instruction is replaced by running each milestone's checks autonomously (noted in NOTES.md).

## Success criteria
1. `npx tsc --noEmit` passes and `npx expo lint` (ESLint installed and configured non-interactively) reports zero errors and zero warnings.
2. `npm test` (Vitest) passes and includes tests for: scoring and multipliers (incl. 2x and boss); streak (same day, next day, 2+ day gap, displayed-as-0 rule); rank thresholds and progress; serve order (starter → due rematch → queue → rematch while waiting → status card); rematch scheduling (≥5 non-rematch cards, not-the-one-just-answered, right removes / wrong moves to back, max 30 dropping oldest); skip (no points, combo unchanged, skipped rematch to back); "card was wrong" reversal (combo restored, `answered` −1, removed from `missed`, title added to `recent`); 2x assignment rules (never boss/rematch/starter; ~12% with a seeded RNG); boss rule (~18% per slot, at most one per batch, seeded RNG); background policy (cancel the in-flight request after >60 s in background, keep arrived cards; save on background); celebration decisions (promotion, every 5th in a row, streak up on first answer of the day); verdict words (boss right → "Boss down."); haptic pattern choice; swipe-to-advance gating (answered and not mid-scroll); prefetch/retry policy (threshold, first-answer gate, one-at-a-time, no retry on 429, one retry after 3 answers); the feed controller enqueuing a card on each `card` event while the stream is still open; `normalize` (duplicate `bad_line`, missing `correct`, duplicate options, tabs, over-long fields truncated, option shuffle keeps the right answer); all 6 starter cards normalizing with stable ids `starter-1`…`starter-6` across repeated runs and card 3 `double`; NDJSON reader with chunk boundaries splitting lines and JSON objects; plan maker (5 slots, ≤1 boss, weights, domain avoids the device's previous one when there's a choice); prompt builder (a snapshot test proving the §8.3 prompt text is used verbatim with the placeholders filled, `recent` capped at 20, trimmed to 60 chars, newlines stripped, "Do not repeat" line omitted when empty, unknown domains ignored); rate limiter (per device and per IP, daily cap); request validation (4 KB cap, unknown fields rejected).
